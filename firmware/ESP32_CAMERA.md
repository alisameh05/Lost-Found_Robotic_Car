# ESP32-CAM firmware and acquisition protocol

## T2 selected interface

The selected target is `esp32:esp32:esp32cam` (AI Thinker). The firmware requires the RHYX/GC2145 sensor from the supplied reference. The driver captures QVGA RGB565 into one buffer and uses Espressif's bounded software JPEG conversion, preserving the timestamp of the first DMA buffer. Each encoded image fits the firmware's fixed 64 KiB output buffer. A resolution, sensor, firmware build, or network change requires new compatibility evidence.

### Build and connect

Use `python firmware/build_esp32_camera.py --arduino-data <Arduino15> --config <protected-config.json> --output <fresh-protected-directory>`. The local config has `ssid`, `password`, `port` and `token`. Use an approved WPA2 network and a random 32-byte token encoded as 64 lowercase hex characters. The peer uses a bearer token within that protected LAN. Keep listening ports off the public internet. The built files and temporary compiler data contain device secrets. Keep them in the user's protected Windows app-data directory. `--compile-only` uses placeholder settings and produces a distinct compile record.

The serial console at 115200 reports the selected private address and port when the camera server is ready. Use that address in the validated Device `interfaces.json`. Set `esp32_cam` to the `target`, `firmware_sha256`, `tools`, `cores` and `libraries` from the generated `camera-build.json`. Store that build artifact and [the v1 contract](esp32_camera/contract.v1.json) as SHA-256-addressed artifacts. The camera selection points to their hashes in `build_artifact_sha256` and `contract_sha256`. It also records `identity`, `variant`, `address`, `port` and `protocol_version`. Set the bundle's `protected_network_sha256` and write the same bearer token into `<LAF_DATA_ROOT>/device/camera.token`. The camera advertises the unique build ID, which binds the running peer to the local build record. Upload verification checks the actual flashed bytes. ## T6 wire and age verification

Each request opens a bounded local HTTP connection. The clock endpoint returns an empty response and the `X-LAF-Clock` header. Its `X-LAF-Request` challenge is a fresh 128-bit lowercase hexadecimal nonce. `X-LAF-Epoch` is `0` before discovery or the expected boot and stream epochs concatenated. The response echoes both request values, then reports the running build, actual epochs, and the device's receive and transmit times. The receive time is sampled at handler entry and the transmit time immediately before serializing the response. The frame endpoint uses its `X-LAF-Frame` header followed by exactly `Content-Length` JPEG bytes. Response fields are separated by one ASCII space. The build ID and both epochs are independently generated 128-bit lowercase hexadecimal values. Numeric values use unsigned decimal. Sequence starts at one and strictly increases with acquisition timestamps within the epoch. New firmware startup creates new epochs. Wi-Fi retries retain original timing and identity.

The backend bounds the full round trip `t3 - t0`, with host time sampled before opening the connection and after receiving the complete reply. The camera processing duration is `t2 - t1`. Define the conservative guard `g = ceil(1000 × (t3 - t0) / 1,000,000) + 2` microseconds. The initial host-minus-camera offset interval is `[t0 - t1 - g, t3 - t2 + g]`. Reject wrong echoes, negative durations, reversed intervals, over-budget RTT, processing longer than the RTT and guard, and over-budget interval width. Extend both interval edges by the same drift/tick guard over the largest distance from capture time to either device exchange timestamp. The full extended interval width must fit `clock_uncertainty_limit_us`. The oldest plausible acquisition is `capture_us + extended_offset_low`. Subtract that from backend receive time, round age upward, and add elapsed backend time through decode, video queueing and acknowledgment. A negative age or any unbounded age invalidates eligibility. A selected deployment must qualify the drift assumption and all numeric profile bounds on its own connection.

The backend reuses one validated acquisition for preview and matching. Each subscriber has one send plus one waiting frame. Inference has the same bound at its worker boundary. The display clock starts with the frame's original acquisition eligibility and expires independently of event heartbeats. Duplicate, regressed and retired-epoch deliveries cannot update it. Browser decode and draw must succeed before the frame is acknowledged. The candidate review retains the exact acquisition's JPEG and overlay coordinates. A backend clock estimate is refreshed halfway through its maximum synchronization interval, and expiry makes robot video unavailable. A change of epoch invalidates display eligibility and revokes any affected lease. Recovery requires the existing explicit Resume path.

## Selected-device bench record

The configured AI Thinker build for the approved WPA2 network has application image SHA-256 `2afed03ab3c317ccd7c8497a90d609f92d0b4da04fcea2c53f912f47c4cb4fce`. Arduino CLI identified the ESP32-D0WDQ6 on the serial bridge and verified the bytes after uploading. The serial console showed normal SPI flash boot followed by repeated `Brownout detector was triggered` resets on the shared driver supply. The camera did not advertise an endpoint during that run. The camera path remains unavailable until the board starts on stable power and the selected local endpoint is measured. Camera transport timing, physical preview, matching and loss/recovery measurements are open.
